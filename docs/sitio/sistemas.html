ADMINISTRACIÓN DE SISTEMAS OPERATIVOS · DOCENTE SINDONI, CARINA

Del servidor recién instalado a un servidor endurecido: un solo hilo

La 1ª entrega dejó el servidor de pie: Ubuntu Server 24.04, red estática, pila LAMP y el SGRSI desplegado. La 2ª entrega lo administra y lo protege: SSH con llaves, respaldos de largo plazo y scripts de automatización. Esta página las presenta entrelazadas, tal como vive el servidor real.

Hilo conductor: 1ª ENTREGA instaló y desplegó → 2ª ENTREGA aseguró el acceso, garantizó la continuidad de datos y dejó la administración automatizada con scripts.

Bloque A · 1ª ENTREGA Relevamiento, instalación y despliegue

A1 · Relevamiento del sistema operativo para el servidor

Antes de instalar, se analizaron alternativas en función de los requerimientos del SGRSI: estabilidad, compatibilidad con la pila tecnológica (Apache, PHP, MariaDB), facilidad de administración y soporte a largo plazo.

A2 · Manual de instalación del S.O. servidor

Se documentó el procedimiento completo (12 pasos) para el técnico: descarga y verificación SHA-256 de la ISO, creación del pendrive con Rufus o dd, y la instalación con Subiquity: idioma, teclado, tipo Ubuntu Server, red en DHCP (se fija luego), mirror ubuntu.mirror.edu.uy, particionado (/boot 512MB, swap 2GB, /), perfil sgrsi-admin en host sgrsi-server, instalación de OpenSSH y reinicio. Verificación post-instalación:

lsb_release -a                # versión instalada
ping -c 4 8.8.8.8             # conectividad
sudo systemctl status ssh     # servicio SSH
sudo apt update && sudo apt upgrade -y   # primer mantenimiento

A3 · Instalación y configuración de la red

IP estática con Netplan sobre enp0s3 y firewall UFW con solo los puertos necesarios. Los parámetros de red asignados son los que usará la 2ª entrega para el acceso remoto por SSH.

Bloque B · 2ª ENTREGA SSH, respaldos y automatización

B1 · Configuración del servicio SSH: llaves públicas (endurece el punto de partida de A2/A4)

OpenSSH pasó de la instalación por defecto a una configuración endurecida: autenticación por llaves públicas Ed25519, sin contraseñas, y directivas de seguridad sobre sshd_config.

DirectivaValorJustificación
PermitRootLogin nonoSe accede con sgrsi-admin + sudo, nunca como root.
PubkeyAuthentication yesyesLogin por par de llaves (requisito de la rúbrica).
PasswordAuthentication nonoTras distribuir las llaves: bloquea fuerza bruta.
AllowUsers sgrsi-adminlista blancaSolo el administrador del SGRSI puede conectarse.
MaxAuthTries 3 / LoginGraceTime 303 / 30 sLimita intentos y tiempo de login.
ClientAliveInterval 300 / ClientAliveCountMax 2—Corta sesiones inactivas (10 min).
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak   # respaldo previo
ssh-keygen -t ed25519 -C "sgrsi-admin@pixelmind"          # par de llaves (passphrase)
ssh-copy-id -i ~/.ssh/id_ed25519.pub sgrsi-admin@192.168.1.50
sudo sshd -t && sudo systemctl restart ssh                # validar y aplicar
ssh -i ~/.ssh/id_ed25519 sgrsi-admin@192.168.1.50         # ingresar SIN contraseña
Regla de seguridad: no cerrar la sesión activa hasta probar en una segunda terminal que el login por llave funciona; con PasswordAuthentication no, quedarse afuera dejaría el servidor inaccesible.

B2 · Medios de respaldo a largo plazo y alta disponibilidad

Se protege todo lo producido en la 1ª entrega (código, configuración y BD) y lo que siga creciendo. Estrategia 3-2-1: 3 copias de los datos, en 2 medios distintos, 1 fuera del servidor.

TipoMedio / destinoFrecuenciaRetención
Copias completas semanalesDisco local + NAS institucionalSemanal4 semanas
Respaldo mensualMedio removible / NASMensualExtendida (año)
Sincronización al servidor de respaldoServidor standby (rsync)Semanal—

Rotación Abuelo-Padre-Hijo (GFS): el respaldo diario («hijo») rota cada 24 h; el semanal («padre») se conserva 1 semana; el mensual («abuelo») se conserva 12 meses. RPO objetivo: pérdida máxima aceptada de 1 día de trabajo; RTO: restauración desde el último dump validado.

🎬 Entrelace: la estrategia da respuesta concreta al riesgo R3 de Ingeniería de Software (pérdida de datos por falla del equipo): no queda en el papel, la implementa SO con dumps MySQL + NAS + standby.

B3 · Rutinas de backup y scripts de automatización

Los respaldos se ejecutan automáticamente con cron usando los scripts modulares. Tabla resumen de la planificación en crontab:

HorarioMóduloFunción
0 2 * * *backup_completo.shDump de BD + copia de archivos → /backup/sgrsi/
0 3 * * 0rsync a NASSync semanal rsync -a --delete al respaldo NAS
0 4 1 * *respaldo_mensual.shCopia mensual con retención extendida (GFS)
0 5 * * *verificar_estado.shAlerta si el último respaldo tiene más de 24 h

Cada script escribe en /var/log/sgrsi-backup.log la fecha, el tamaño generado y el resultado; el verificador alerta ante respaldos viejos. Las credenciales viven en un archivo protegido de solo root, no dentro de los scripts.

B4 · Primera versión del script modular del servidor (administra todo lo desplegado en A4)

Kit shell real que acompaña al documento en el repositorio (docs/sistemas_operativos/scripts/), con menú principal sgrsi-admin.sh y módulos independientes ejecutables también por cron: comunes.sh (funciones compartidas), backup_completo.sh, respaldo_mensual.sh, restaurar_bd.sh, verificar_estado.sh, actualizar_sistema.sh y gestion_ssh.sh. Todos validados con bash -n.

MóduloQué automatiza
sgrsi-admin.shMenú interactivo de administración del servidor.
backup_completo.shRespaldo completo (BD + archivos) con log.
respaldo_mensual.shRespaldo mensual con retención extendida y rotación GFS.
restaurar_bd.shRestauración del último dump validado (RTO).
verificar_estado.shEstado de servicios y antigüedad de respaldos.
actualizar_sistema.shRutina segura apt update/upgrade/autoremove.
gestion_ssh.shRespaldo y revisión de configuración SSH.
Conclusión del hilo conductor: la 1ª entrega puso el servidor en producción (instalación, red estática y LAMP con el SGRSI desplegado); la 2ª lo blindó —SSH con llaves sin contraseñas—, garantizó su continuidad (respaldos 3-2-1 con rotación GFS) y dejó la administración repetible con scripts modulares programados en cron.
