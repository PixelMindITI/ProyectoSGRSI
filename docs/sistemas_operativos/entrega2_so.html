1 · Configuración del servicio SSH en el servidor

En la primera entrega se instaló OpenSSH Server con valores por defecto. En esta segunda entrega se ajusta el servicio a los requerimientos del SGRSI: acceso remoto seguro para el administrador, autenticación por llaves públicas (sin contraseñas) y endurecimiento de la configuración.

1.1 Endurecimiento de sshd_config

Editamos el archivo de configuración del demonio SSH:

sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak   # respaldo previo
sudo nano /etc/ssh/sshd_config

Parámetros ajustados (buscar cada directiva o agregarla al final):

DirectivaValorJustificación
Port 2222 (documentado)Se mantiene el puerto estándar documentado en la 1ª entrega; si la política institucional lo permite puede cambiarse a un puerto alto (p. ej. 2222) para reducir escaneos automáticos.
PermitRootLogin nonoNunca se accede como root directamente; se usa sgrsi-admin + sudo.
PubkeyAuthentication yesyesHabilita el login por par de llaves (requisito de la rúbrica).
PasswordAuthentication nonoTras distribuir las llaves se desactiva el login por contraseña: bloquea ataques de fuerza bruta.
KbdInteractiveAuthentication nonoDesactiva métodos interactivos alternativos de contraseña.
AllowUsers sgrsi-adminlista blancaSolo el usuario administrador del SGRSI puede conectarse.
MaxAuthTries 33Limita intentos fallidos por conexión.
LoginGraceTime 3030 segTiempo máximo para completar el login.
X11Forwarding nonoUn servidor headless no necesita forwarding gráfico.
ClientAliveInterval 300
ClientAliveCountMax 2		—Corta sesiones inactivas (10 min), liberando conexiones colgadas.
# Validar sintaxis y aplicar los cambios
sudo sshd -t
sudo systemctl restart ssh
sudo systemctl status ssh

1.2 Autenticación por llaves públicas

Paso 1 — Generar el par de llaves en el equipo cliente

# En la PC del administrador (Windows PowerShell o Linux)
ssh-keygen -t ed25519 -C "sgrsi-admin@pixelmind"
# Aceptamos la ruta por defecto (~/.ssh/id_ed25519) y definimos
# una passphrase para proteger la clave privada.
Se elige Ed25519 por ser el algoritmo moderno recomendado: claves cortas, rápido y criptográficamente más seguro que RSA-2048.

Paso 2 — Distribuir la llave pública al servidor

# Opción A (Linux/Mac/Git Bash): copia automática
ssh-copy-id -i ~/.ssh/id_ed25519.pub sgrsi-admin@192.168.1.50

# Opción B (Windows PowerShell): crear el directorio y anexar manualmente
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh sgrsi-admin@192.168.1.50 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

Paso 3 — Verificar el acceso por llave

ssh -i ~/.ssh/id_ed25519 sgrsi-admin@192.168.1.50
# Debe entrar SIN pedir contraseña del servidor
# (solo la passphrase de la clave privada, si se definió).
Regla de seguridad: NO cerrar la sesión actual hasta probar en una segunda terminal que el login por llave funciona. Con PasswordAuthentication no, quedarse afuera significaría perder el acceso remoto.

1.3 Protección adicional del servicio

# Limitar intentos por IP en UFW (complemento a MaxAuthTries)
sudo ufw limit ssh/tcp

# Opcional recomendado: fail2ban bloquea IPs con intentos repetidos
sudo apt install fail2ban -y
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd   # ver IPs baneadas

1.4 Verificación final (checklist de la rúbrica)

✔ComprobaciónComando
☐Servicio activo y habilitado al arranque.systemctl status ssh
☐Login remoto funcionando desde otro equipo de la red.ssh sgrsi-admin@192.168.1.50
☐Llave pública instalada en ~/.ssh/authorized_keys.cat ~/.ssh/authorized_keys
☐Login por contraseña rechazado.ssh -o PubkeyAuthentication=no sgrsi-admin@192.168.1.50 → debe fallar.
☐Root no puede conectarse.sudo sshd -T | grep permitrootlogin → no
☐Firewall con límite de intentos sobre SSH.sudo ufw status verbose

2 · Medios de respaldo a largo plazo y alta disponibilidad

El objetivo es evitar la pérdida de información del SGRSI (base de datos, código y configuración del servidor) ante fallas de hardware, errores humanos, ataques o desastres físicos.

2.1 ¿Qué se respalda?

DatoOrigenFrecuenciaCriticidad
Base de datos sgrsi_dbMariaDB (mysqldump lógico)DiariaAlta: tickets, préstamos, solicitudes e inventario.
Aplicación SGRSI/var/www/html/sgrsiDiaria (código también vive en Git)Media-alta
Configuración del servidor/etc (sshd, netplan, apache2, php)Semanal o al cambiar config.Media: acelera la reconstrucción del servidor.

2.2 Estrategia 3-2-1 y rotación de copias

Aplicamos la regla 3-2-1 estándar de la industria: 3 copias de los datos, en 2 medios distintos, con 1 copia fuera del servidor.

NivelMedioContenidoRetención
Local rápidaDisco secundario /backup del propio servidorCopias diarias (BD + app + config)7 días (se sobreescriben)
Externa semanalUnidad externa / NAS de la institución montada en /mnt/respaldo-nasRespaldo completo semanal comprimido4 semanas (esquema abuelo-padre-hijo)
Largo plazo mensualAlmacenamiento en nube institucional (Google Drive / OneDrive vía rclone) u otro sitio físicoRespaldo mensual cifrado (.tar.gz + sha256)12 meses — cumplimiento a largo plazo
Esquema Abuelo-Padre-Hijo (GFS): el respaldo diario («hijo») rota cada semana; el semanal («padre») se conserva un mes; el mensual («abuelo») se conserva un año. Equilibra espacio y profundidad histórica.

2.3 Alta disponibilidad de los datos

MedidaDescripciónEstado
RAID 1 (discos espejados) en el servidorSi un disco falla, el sistema sigue operando con el espejo sin pérdida de datos.Recomendado para producción; verificable con cat /proc/mdstat.
Servidor de respaldo (standby)Copia completa del entorno lista para asumir si el principal cae.Se implementa en la 3ª entrega según la letra; esta entrega deja preparados scripts y procedimiento.
Replicación MariaDB (futura)Master → réplica que se mantiene sincronizada en tiempo casi real.Evolución natural para la 3ª entrega junto al servidor de respaldo.
Código en repositorio Git remotoLa aplicación siempre es recuperable desde GitHub aunque el servidor se pierda.Activo (repositorio privado del grupo).

2.4 Objetivos de recuperación (RPO / RTO)

IndicadorSignificadoMeta SGRSI
RPO (Recovery Point Objective)Cuántos datos podemos perder como máximo.≤ 24 h (respaldo diario); ≤ 1 semana para datos no transaccionales gracias al NAS.
RTO (Recovery Time Objective)Cuánto tarda el servicio en volver a estar operativo.≤ 4 h restaurando en el mismo servidor; ≤ 1 día en hardware alternativo usando este manual.

3 · Rutinas de backup y scripts de automatización

Los respaldos se ejecutan automáticamente con cron mediante los scripts modulares de la sección 4, evitando dependencia de la memoria humana.

3.1 Preparación del entorno

# Disco/carpeta destino de los respaldos locales
sudo mkdir -p /backup/sgrsi/{db,app,config}
# Credenciales en archivo protegido (no van dentro del script)
sudo nano /root/.sgrsi_backup.cnf
[client]
user=sgrsi_user
password='ClaveSegura123!'
sudo chmod 600 /root/.sgrsi_backup.cnf
El usuario de MariaDB necesita el privilegio LOCK TABLES y SELECT sobre sgrsi_db.*, que ya posee por GRANT ALL.

3.2 Programación con cron

sudo crontab -e    # tareas del root (los scripts están en /opt/sgrsi-admin)
HorarioTareaLínea crontab
Todos los días 02:00Backup diario BD + aplicación + configuración0 2 * * * /opt/sgrsi-admin/modulos/backup_completo.sh >> /var/log/sgrsi-backup.log 2>&1
Domingos 03:00Sincronizar semanal al NAS0 3 * * 0 rsync -a --delete /backup/sgrsi/ /mnt/respaldo-nas/semanal/
1º de cada mes 04:00Copia mensual a largo plazo (nube) + limpieza de rotación0 4 1 * * /opt/sgrsi-admin/modulos/respaldo_mensual.sh >> /var/log/sgrsi-backup.log 2>&1
Todos los días 05:00Verificación de servicios y espacio (alerta temprana)0 5 * * * /opt/sgrsi-admin/modulos/verificar_estado.sh >> /var/log/sgrsi-estado.log 2>&1

3.3 Verificación y prueba de restauración

Un backup no verificado no es un backup. Rutina mensual recomendada:

# 1) Comprobar integridad del dump
gzip -t /backup/sgrsi/db/sgrsi_db_$(date +\%Y\%m\%d).sql.gz

# 2) Restaurar en una base de PRUEBA (nunca directo sobre producción)
mysql -u sgrsi_user -p -e "CREATE DATABASE sgrsi_prueba"
gunzip < /backup/sgrsi/db/sgrsi_db_20260801.sql.gz | mysql -u sgrsi_user -p sgrsi_prueba
mysql -u sgrsi_user -p -e "SELECT COUNT(*) FROM sgrsi_prueba.usuarios;"
mysql -u sgrsi_user -p -e "DROP DATABASE sgrsi_prueba"

3.4 Registro de ejecuciones

Cada script escribe en /var/log/sgrsi-backup.log fecha, tamaño generado y resultado; el módulo verificar_estado.sh alerta si el último respaldo tiene más de 24 horas o si el disco supera el 85 % de uso.

4 · Primera versión del script modular del servidor

El kit de administración se organiza en módulos pequeños y reutilizables (criterio de la rúbrica): una librería común y un módulo por tarea, invocados desde un menú principal o directamente por cron. Los archivos reales acompañan este documento en docs/sistemas_operativos/scripts/ del repositorio.

4.1 Estructura modular

ArchivoRol del módulo
sgrsi-admin.shMódulo principal: menú que conecta todos los módulos (fuente de la librería común).
modulos/comunes.shLibrería compartida: variables globales, colores, funciones de log y verificaciones previas.
modulos/backup_completo.shRespaldo diario: mysqldump + tar de aplicación y configuración, con rotación local.
modulos/respaldo_mensual.shCopia mensual a largo plazo (carpeta mensual + hash SHA-256; envío a nube con rclone si está configurado).
modulos/restaurar_bd.shRestauración segura de un dump elegido (con confirmación explícita).
modulos/verificar_estado.shSalud del servidor: servicios, disco, memoria, vigencia del último backup.
modulos/actualizar_sistema.shActualizaciones APT con registro.
modulos/gestion_ssh.shEstado del servicio SSH y listado de llaves autorizadas.

4.2 Módulo principal — menú (extracto)

#!/usr/bin/env bash
# sgrsi-admin.sh - Menu principal de administracion PixelMind
set -euo pipefail
DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$DIR/modulos/comunes.sh"          # libreria comun

while true; do
  echo -e "${TITULO}=== SGRSI :: Administracion del servidor ===${NC}"
  echo " 1) Respaldo completo (BD + app + config)"
  echo " 2) Respaldo mensual a largo plazo"
  echo " 3) Restaurar base de datos"
  echo " 4) Verificar estado del servidor"
  echo " 5) Actualizar sistema"
  echo " 6) Gestion SSH"
  echo " 0) Salir"
  read -rp "Opcion: " op
  case "$op" in
    1) bash "$DIR/modulos/backup_completo.sh" ;;
    2) bash "$DIR/modulos/respaldo_mensual.sh" ;;
    3) bash "$DIR/modulos/restaurar_bd.sh" ;;
    4) bash "$DIR/modulos/verificar_estado.sh" ;;
    5) bash "$DIR/modulos/actualizar_sistema.sh" ;;
    6) bash "$DIR/modulos/gestion_ssh.sh" ;;
    0) salir ;;
    *) error "Opcion invalida" ;;
  esac
done

4.3 Librería común — comunes.sh (extracto)

# Variables globales compartidas por todos los modulos
BD_NOMBRE="sgrsi_db"; BD_USUARIO="sgrsi_user"
BD_CNF="/root/.sgrsi_backup.cnf"
BACKUP_DIR="/backup/sgrsi"; APP_DIR="/var/www/html/sgrsi"
RETENCION_DIAS=7; USO_MAX_DISCO=85

# Colores / funciones de log usadas por los modulos
NC='\033[0m'; TITULO='\033[1;34m'; OK='\033[1;32m'; ERROR='\033[1;31m'
info(){ echo -e "${OK}[INFO]$(date '+ %F %T') $*${NC}"; }
error(){ echo -e "${ERROR}[ERROR] $(date '+%F %T') $*${NC}" >&2; exit 1; }
requiere_root(){ [ "$(id -u)" -eq 0 ] || error "Ejecutar como root (sudo)"; }

4.4 Instalación en el servidor

sudo mkdir -p /opt/sgrsi-admin/modulos
# copiar los scripts desde el repositorio y dar permisos de ejecución
sudo chmod +x /opt/sgrsi-admin/sgrsi-admin.sh /opt/sgrsi-admin/modulos/*.sh
sudo /opt/sgrsi-admin/sgrsi-admin.sh        # ejecución manual por menú

4.5 Ventajas del diseño modular

  • Mantenimiento: cada tarea vive en su archivo; corregir el backup no toca el resto.
  • Reutilización: cron llama a los mismos módulos que el menú (una sola lógica).
  • Depuración: se prueba cada módulo aislado (bash modulos/verificar_estado.sh).
  • Escalabilidad: para la 3ª entrega se agregarán módulos nuevos (contenedores, servidor de respaldo) sin reescribir lo existente.
